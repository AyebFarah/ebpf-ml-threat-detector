# TCP Collector — Design and Implementation

## 1. Purpose

The TCP collector was added to provide TCP flow-level visibility that is not available from Tetragon `tcp_connect` events alone.

While Tetragon tells us that a connection was established, the TCP collector provides information about the complete observed flow, including:

- Connection duration
- Packets sent and received
- Bytes sent and received
- Source and destination
- Flow termination reason

This enriches the data available for later correlation and ML-based threat detection.

## 2. Why a TCP Collector?

A `tcp_connect` event only represents the beginning of a connection. It does not directly tell us how much communication occurred afterward.

The TCP collector therefore complements Tetragon:

```text
Tetragon
   │
   └── tcp_connect
       → connection established

TCP Collector
   │
   └── tcp_flow
       → duration
       → packets
       → bytes
       → termination reason
```

This distinction is useful for detecting behaviors such as:

- Very short connections
- Large data transfers
- Unusual packet/byte ratios
- Repeated connections
- Connections that terminate unexpectedly

## 3. Flow-Based Design

The collector aggregates individual TCP packets into a flow instead of generating one event per packet.

Each flow is identified using the TCP connection tuple:

- `src_ip`
- `src_port`
- `dst_ip`
- `dst_port`
- `transport`

The collector maintains counters while the connection is active and produces a single `tcp_flow` event when the flow ends.

This significantly reduces event volume while preserving useful traffic statistics.

## 4. Collected Information

A TCP flow contains information such as:

- `src_ip` / `src_port`
- `dst_ip` / `dst_port`
- `transport`
- `start_ts`
- `end_ts`
- `duration_seconds`
- `packets_sent`
- `packets_received`
- `bytes_sent`
- `bytes_received`
- `termination_reason`

For example:

```text
[TCP FLOW] 192.168.1.10:36994 -> 151.101.130.137:443
reason=collector_stopped
dur=0.811446
pkts=10/10
bytes=3547/2651
```

## 5. Integration with the Pipeline

TCP events are written to:

```text
samples/collectors_events/tcp_events.jsonl
```

The normalizer converts them into the common event format with:

- `source = "tcp"`
- `event_type = "tcp_flow"`

The correlator then attempts to associate the flow with the corresponding Tetragon `tcp_connect` event using:

- 5-tuple + start timestamp

The 5-tuple is:

* src_ip
* dst_ip
* src_port
* dst_port
* transport

A configurable tolerance is used:

-`TCP_FLOW_TIME_TOLERANCE_SECONDS = 5`

This is necessary because the packet capture timestamp and the kernel-level Tetragon timestamp are generated by different observation mechanisms and may not be exactly identical.

This allows the final correlated event to combine:

- TCP connection
- DNS information
- TLS/JA4 information
- SSH information
- TCP flow statistics

## 6. Design Choice

The collector intentionally focuses on flow metadata rather than packet payloads.
Overall, the TCP collector complements the existing Tetragon observation by transforming low-level TCP activity into compact, flow-level behavioral features suitable for correlation and machine-learning analysis.
